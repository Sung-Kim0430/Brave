## 1. P0-1 评论被整体转义（必现）

**位置**：`core/App.php:570-575`

```php
// Fast path: simple safe tags that don't need full parsing
if (preg_match('/^<(p|br|strong|em|b|i)>.*<\/\1>$/s', $html) &&
    !preg_match('/<script|<iframe|<object|javascript:/i', $html)) {
    // Still escape for safety but skip DOMDocument overhead
    return htmlspecialchars($html, ENT_QUOTES, 'UTF-8');   // ← 把合法标签也转义了
}
```

**链路取证**（全部本地实跑）

1. `functions.php:31` 设 `commentsMarkdown = true` → Typecho `Widget\Base\Comments::___content()` 走 `Utils\Markdown::convert()` → HyperDown。
2. 实跑 HyperDown（`Parser.php` 单文件）：

   | 输入 | `makeHtml()` 输出 |
   |------|-------------------|
   | `祝你们幸福` | `<p>祝你们幸福</p>` |
   | `第一段\n\n第二段` | `<p>第一段</p><p>第二段</p>` |
   | `<strong>hi</strong>` | `<p><strong>hi</strong></p>` |

   → 输出**无前导换行**，正好命中 `^<(p|…)>…</\1>$`。
3. `Common::stripTags($text, '<p><br>' . $commentsHTMLTagAllowed)` 保留 `<p>`。
4. `commentPage.php:67` → `App::sanitizeCommentHtml()` → 实跑结果：

   ```
   C1  <p>你好</p>              => &lt;p&gt;你好&lt;/p&gt;
   C2  <p>a</p><p>b</p>        => &lt;p&gt;a&lt;/p&gt;&lt;p&gt;b&lt;/p&gt;
       <p>a<br>b</p>           => &lt;p&gt;a&lt;br&gt;b&lt;/p&gt;
   C13 <p>x</p> 后面还有字       => <p>x</p> 后面还有字   ← 未命中，正常渲染
   C7  <del>x</del>             => <del>x</del>          ← 正常（不在 fast path 名单里）
   ```

**触发条件**：内容以 `<p>/<br>/<strong>/<em>/<b>/<i>` 开头并以同类结束标签结尾（`/s` 让 `.*` 跨行贪婪吞到最后一个 `</p>`，`$` 容忍末尾换行）→ **单段与多段评论全部命中**。

**影响**
- 祝福板所有正常评论显示为 `<p>祝你们幸福</p>` 之类的原始标签文本。
- 同一根因导致 `loveListTitleAllowHtml=1`（后台文案承诺支持 `<del><code><strong><em><br>`）实际只有 `<del>/<code>` 生效，`<strong>/<em>/<br>` 被转义 —— 开关说明与实现不符。
- 方向是"过度转义"，不构成 XSS，但属于防御性代码反向破坏功能。

**修复建议**（任选，推荐 A）

```php
// A. 删除 fast path，统一走 DOM 分支（该分支已做完整白名单校验）
-        // Fast path: simple safe tags that don't need full parsing
-        if (preg_match('/^<(p|br|strong|em|b|i)>.*<\/\1>$/s', $html) &&
-            !preg_match('/<script|<iframe|<object|javascript:/i', $html)) {
-            // Still escape for safety but skip DOMDocument overhead
-            return htmlspecialchars($html, ENT_QUOTES, 'UTF-8');
-        }
```
保留 `strpos($html, '<') === false` 的纯文本 fast path（`App.php:566`，该分支行为正确且是主要性能收益）。

```php
// B. 若担心性能，把 fast path 改成"结构校验后原样放行"，必须在返回前再确认不含任何非白名单标签：
if (preg_match('/^<(p|br|strong|em|b|i)>.*<\/\1>$/s', $html)
    && !preg_match('/<(?!\/?(?:p|br|strong|em|b|i)\b)[^>]*>/i', $html)) {
    return $html;   // 已确认只有白名单标签
}
```
B 的风险面更大（一旦正则写错就是 XSS），A 更稳。

**根因反思**：`tests/` 的 30 个用例全部是「源文件字符串契约」匹配（`assert.match(read('core/App.php'), …)`），没有一条断言运行结果，所以这类逻辑回归 CI 完全抓不到。

## 2. P1-1 / P1-2 自定义代码守卫：白名单失效 + 误拦合规脚本

**位置**：`base/head.php:150-158`、`base/footer.php:233-241`（两处逻辑重复）

```php
$siteHost = parse_url(App::optionValue('siteUrl', ''), PHP_URL_HOST);
$trustedHosts = array('cdn.staticfile.org', $siteHost);
$trustedPattern = implode('|', array_map('preg_quote', $trustedHosts));

if (preg_match('/<script[^>]*src\s*=\s*["\']?(?!https?:\/\/(' . $trustedPattern . '))/i', $customHead)) {
    echo '<!-- Custom header blocked: ... -->';
} else {
    echo $customHead;
}
```

**问题 1：`["\']?` 可选导致负向先行被"跳过"**，实测（PHP 8.5，`$siteHost='blog.example.com'`）：

| 输入 | 期望 | 实测 |
|------|------|------|
| `<script src="https://cdn.staticfile.org/jquery…">` | 放行 | **被拦截** ❌ |
| `<script src='https://cdn.staticfile.org/a.js'>` | 放行 | **被拦截** ❌ |
| `<script src="https://blog.example.com/a.js">` | 放行 | **被拦截** ❌ |
| `<script src=https://cdn.staticfile.org/a.js>` | 放行 | 放行 ✅ |
| `<script src="https://evil.example.com/a.js">` | 拦截 | 被拦截 ✅（巧合） |

原因：引号可选 → 正则可在「未消费引号」的位置评估负向先行，此时位置上是 `"https://…`，`https?:\/\/` 不匹配 → `(?!…)` 成功 → 整体判定为「不可信」。结果：**白名单形同虚设，站长开启 `enableCustomCode` 后添加的任何带引号的合规外链脚本都会被静默替换成一行 HTML 注释**（浏览器控制台无报错，只有查看源码才能发现）。

**问题 2**：`parse_url('', PHP_URL_HOST)` 返回 `null`，`preg_quote(null)` 在 PHP 8.1+ 触发 `Deprecated: preg_quote(): Passing null to parameter #1`（已实测复现）；同时空 host 进入 alternation 会产生空分支，进一步削弱判定。

**修复建议**：不要用负向先行做域名校验，改为「提取 src → 解析 host → 白名单比对」：

```php
$siteHost = (string)parse_url(App::optionValue('siteUrl', ''), PHP_URL_HOST);
$trustedHosts = array_filter(array('cdn.staticfile.org', $siteHost), function ($h) {
    return trim((string)$h) !== '';
});

$blocked = false;
if (preg_match_all('/<script\b[^>]*\bsrc\s*=\s*(?:"([^"]*)"|\'([^\']*)\'|([^\s"\'>]+))/i', $customHead, $m, PREG_SET_ORDER)) {
    foreach ($m as $match) {
        $src = $match[1] !== '' ? $match[1] : ($match[2] !== '' ? $match[2] : $match[3]);
        $host = parse_url($src, PHP_URL_HOST);
        if ($host === null || !in_array(strtolower($host), $trustedHosts, true)) {
            $blocked = true;
            break;
        }
    }
}
if ($blocked) { /* 输出注释 + 明确提示哪个域名被拦 */ }
```
注意：该守卫本身只是"防误配"的软约束（内联 `<script>` 仍会放行，这是 `enableCustomCode` 的设计前提），不要把它当成安全边界；同一实现建议抽到 `App::collectUntrustedScriptHosts()` 里，避免 head/footer 两份重复代码继续漂移。

## 3. P1-3 `[item …/]` 自闭合语法是死分支

**位置**：`core/App.php:202`

```php
preg_match_all('/\[item\b([^\]]++)(?:\/\]|\]((?:[^\[]|\[(?!\/item\]))*+)\[\/item\])/i', …)
```

`([^\]]++)` 是**占有量词**，会连 `/` 一起吃掉，且不可回溯 → `(?:\/\]…)` 永远匹配不到。实测：

| 输入 | match | 结果 |
|------|-------|------|
| `[item status="1"/]` | 0 | ❌ 不解析 |
| `[item status="1" /]` | 0 | ❌ 不解析 |
| `[item status="1"]t[/item]` | 1 | ✅ |

后果：写 `[loveList][item status="1"/][/loveList]` 时，外层 `[loveList]` 包裹被移除、`[item …/]` 原样输出为纯文本（`renderLoveListShortcode` 在无 item 时 `return $content`）。

**修复**（已实测通过）：

```php
preg_match_all('/\[item\b([^\]\/]++)(?:\/\s*\]|\]((?:[^\[]|\[(?!\/item\]))*+)\[\/item\])/i', …)
```

## 4. P2 级问题

### P2-1 PJAX 导航后 `<title>` 不更新
`base/footer.php` 的 `pjax:complete` 只做了 loading 状态清理与 `ensureSiteRuntimeTicker`，全文无 `document.title` 处理（已 grep 确认）。站内跳转后标签页标题/历史记录仍是上一页。

```js
$(document).pjax(selector, '#pjax-container', { fragment: '#pjax-container', timeout: 6000, scrollTo: 0 });
$(document).on('pjax:complete', function (event, xhr) {
    var m = /<title[^>]*>([\s\S]*?)<\/title>/i.exec(xhr.responseText || '');
    if (m) document.title = m[1].trim();
    // …原有逻辑
});
```

### P2-2 全站无 `<h1>`
模板中最高层级是 `index.php` 的 `<h4 class="post-title">`、其余页面的 `<h5>`；`<h1>` 零出现。文章页标题用 `<h5>`、页面导言用 `<h5>`。建议：文章页标题升为 `<h1>`，列表页导言/标题升为 `<h1>`，其余顺延，避免 h1→h4 跳跃。

### P2-3 自定义 CSP 校验过严 + 静默降级
`base/head.php:57` 的合法字符集 `[a-z0-9\s'\-:\/\.\*;_]` 不含 `+ = , " @ % [ ]`，因此含 hash/nonce 的策略（`script-src 'sha256-abc+/='`）会被判非法 → `$cspHeaderSent` 保持 false → 降级输出 `<meta http-equiv="Content-Security-Policy">`。而 meta 形式**不支持 `frame-ancestors` / `report-uri` / `sandbox`**，站点会以为策略已生效。建议放宽字符集（真正必要的是禁止 CR/LF 与 `<`），并在降级时输出 HTML 注释说明原因。

### P2-4 自定义 CSP 与 `style.css` 的 preload 存在耦合
`base/head.php:113`：

```html
<link rel="preload" href="…/style.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="…/style.css"></noscript>
```

内联事件处理器依赖 `script-src 'unsafe-inline'`。默认策略含该指令所以正常；但一旦站长按 §P2-3 的自定义策略收紧（用 hash/nonce 或去掉 `'unsafe-inline'`），`onload` 被 CSP 拦掉 → **全站只剩内联关键 CSS，样式完全丢失**（`<noscript>` 不生效）。建议：文档中明确「自定义 CSP 必须保留 `script-src 'unsafe-inline'`，否则需同步改回同步加载 style.css」，或把关键 CSS 补全后直接同步加载完整样式表。

### P2-5 `[loveList]` 的作用域与文档不符
全仓库只有 `loveListPage.php:43` 调用 `App::parseShortCode()`；`post.php` 的 `$this->content()` 直出。而 `docs/USAGE.md` 写「格式示例（在文章/页面内容里使用）」。二选一：在 `post.php` 也套一层 `parseShortCode`（正文含 `[loveList` 才解析，成本可忽略），或把文档改为「仅恋爱清单页生效」。

## 6. P3 清单（低优先级 / 可维护性）

1. **SSRF 防护是死代码**：`App::normalizeUrl()` 中 localhost/私有 IP 拦截要求 `$allowRelative === false`（`App.php:302`），但全部调用点（`App.php:98/118/127/212/213/353/462/472`、各模板）都传 `true` → 该分支不可达。`PROJECT_STATUS.md` 把「SSRF 防护增强」列为已修复，与实现不符（实际 PHP 也不会发请求，本就不是真 SSRF）。建议删除误导性分支，或在需要处显式启用严格模式。
2. **死类名**：`is-page-ready`（`main.js:545` 添加，`style.css` 无定义）、`list-wbc`（`index.php:53`）。
3. **Bootstrap 缺 Popper**：本地/CDN 均只加载 `bootstrap.min.js`（实测无 `createPopper`），当前只用到 `collapse` 所以无感；一旦自定义代码里用 dropdown/tooltip/popover 会报错。建议换 `bootstrap.bundle.min.js` 或补 `popper.min.js`。

    public static $opts = array();
    public static function options() {

            public function __isset($n) { return array_key_exists($n, Helper::$opts); }
            public function __get($n)   { return Helper::$opts[$n] ?? null; }
        };
    }
}
require '/path/to/core/App.php';

var_dump(App::sanitizeCommentHtml('<p>祝你们幸福</p>'));   // 期望 <p>祝你们幸福</p>，实际 &lt;p&gt;…&lt;/p&gt;
